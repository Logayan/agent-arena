# 江湖 Online：原始愿景与比赛约束

- 记录日期：2026-07-25
- 文档性质：用户原始需求记录
- 优先级：最高
- 状态：持续澄清中

## 1. 本阶段工作原则

当前仓库视为从 0 开始的预研沙盒。

- 现有代码、文档、架构、页面和 Demo 均不构成产品约束。
- 必要时可以清空、覆盖或整体重做。
- 当前阶段以预研和用户需求确认为主。
- 可以随时制作、修改或丢弃 Demo，用于验证产品想法和用户体验。
- 在用户需求确认之前，不把任何临时技术方案当作正式产品基线。

## 1.1 最终需求文档交付规范

最终用户需求文档必须采用标准 PRD（产品需求文档）风格输出。

PRD 至少应包含：

1. 文档信息与版本记录；
2. 产品背景与问题陈述；
3. 产品愿景、定位和目标；
4. 目标用户与用户需求；
5. 用户场景和核心用户旅程；
6. 产品范围与非目标；
7. 核心业务概念；
8. 完整生产流程；
9. 功能需求及优先级；
10. 业务规则和异常场景；
11. 非功能需求；
12. 数据、产物和状态要求；
13. 成功指标和效果评估；
14. 验收标准；
15. 风险、依赖、假设和待确认事项；
16. 版本规划。

文档编写要求：

- 从用户问题和产品价值出发，不以技术架构作为需求主线；
- 明确区分用户需求、产品方案和技术实现；
- 功能需求应具有编号、优先级和可验收描述；
- 已确认内容、产品假设和待确认事项应明确标注；
- 比赛要求作为阶段性范围和验收约束纳入 PRD；
- Demo 和技术方案用于验证 PRD，不反向代替 PRD；
- 最终 PRD 应能够指导交互设计、技术设计、开发排期和验收测试。

## 2. 用户的最终目标

用户正在参加“多 Agent 协作与对抗实践”比赛，但目标不只是完成比赛。

优先级关系为：

> 首先实现江湖 Online 的长期产品愿景，并在实现愿景的过程中顺带满足比赛要求。

因此：

- 比赛课题是产品的阶段性验收场景，不是产品边界。
- 不围绕某一个比赛案例硬编码系统。
- 比赛 Demo 必须由通用平台能力构建出来。
- 当比赛要求与长期愿景发生取舍时，优先保证愿景，同时寻找满足比赛验收的最小实现路径。

## 3. 产品名称与核心表达

产品名称：

> **江湖 Online**

产品意象：

> 有人的地方就有江湖；有江湖的地方可以构建 Agent，也有 Agent 自己形成的江湖。

“江湖”表达的不只是多个 Agent 的集合，还包括：

- 不同身份、能力、立场和目标的参与者；
- Agent 之间的协作、委托、竞争、质疑、攻防与仲裁；
- 由规则、关系、知识、声誉、权限和利益形成的社会结构；
- 人与 Agent、Agent 与 Agent 共同参与的动态场景；
- 可以被观察、编辑、运行、干预和复盘的智能体世界。

以上解释属于当前需求推导，后续需要用户继续确认。

## 4. 当前产品愿景

江湖 Online 的核心是：

> 根据用户传入的知识构建适合当前场景的多 Agent，并根据用户需求构建一条可编辑、可运行的标准生产流程。多个 Agent 在生产流程的各个步骤中协作与对抗，共同生成步骤产物；步骤产物继续流转到下一步，直到整个生产流程执行完毕并形成最终产物。

这里的“工作流”与比赛题目中的“生产流”含义相同，不是独立于生产任务的另一种产品模式。

### 4.1 知识驱动的多 Agent 构建

平台可以像 MiroFish 一样，根据用户传入的知识、资料或世界背景：

1. 理解知识中的人物、组织、关系、规则、事件和观点；
2. 自动构建一组具有不同身份、能力、知识、立场或目标的 Agent；
3. 建立 Agent 之间的关系和交互环境；
4. 让这些 Agent 参与用户所需生产流程中的协作、竞争、讨论、质疑或对抗；
5. 允许用户查看、编辑和治理生成的 Agent。

### 4.2 需求驱动的标准生产流程构建

当用户希望完成一个真实任务时：

1. 用户输入目标、知识、约束、资源和期望结果；
2. 平台理解用户需求以及完成该需求所需的标准生产流程；
3. 平台自动生成一条生产流程草案；
4. 生产流程由多个具有明确目标、输入、活动和输出的步骤组成；
5. 生产流程对用户可见、可编辑、可保存和可复用；
6. 平台为不同步骤自动安排适合的多个 Agent；
7. Agent 在步骤内部按职责进行分工、信息传递和多轮协作；
8. 在必要步骤中加入质疑、审查、红蓝攻防、竞争方案、投票或仲裁；
9. 多个 Agent 共同生成该步骤要求的正式产物；
10. 步骤产物按照流程定义流转，成为后续步骤的输入或约束；
11. 用户可以在关键节点确认、修改、暂停、接管或终止；
12. 所有步骤完成后，系统汇总并输出最终业务产物。

### 4.3 核心运行闭环

```text
用户需求与知识
-> 理解目标、约束和最终产物
-> 生成可编辑的标准生产流程
-> 生成或选择适合流程的多 Agent
-> 执行当前生产步骤
-> Agent 协作与对抗
-> 生成并确认步骤产物
-> 步骤产物流转到下一步
-> 重复执行直至生产流程结束
-> 输出最终产物与完整过程记录
```

生产流程中的核心流转对象是“步骤产物”，而不是无结构的 Agent 聊天内容。

## 5. 当前核心产品假设

以下内容是根据用户表达形成的待验证假设：

1. 用户不应被迫手工设计所有 Agent，平台应能根据知识和需求自动生成初始 Agent 团队。
2. 自动生成结果不能是黑盒，Agent、关系和生产流程都必须可编辑。
3. 生产流程是完成用户任务的执行骨架，多 Agent 是各生产步骤中的智能执行和质量治理主体。
4. 每个生产步骤都应定义输入、活动、参与 Agent、协作/对抗方式、步骤产物和完成条件。
5. 步骤产物必须结构化、可保存、可审查，并能可靠流转到后续步骤。
6. 协作与对抗不是与生产流程分离的表演，而是用于提高步骤产物质量的执行机制。
7. 协作与对抗不必出现在每一步，应根据步骤特点、风险和质量要求动态配置。
8. 人类用户始终是江湖的参与者或最终治理者，而不是完全被排除在运行之外。

## 5.1 已确认：生产流程与 Agent 的生成依据

江湖 Online 应参考 MiroFish 的核心逻辑：

- 解析用户提供的知识库内容；
- 从知识中识别角色、组织、观点、关系、规则和事件；
- 根据知识内容直接生成多个具有差异性的 Agent；
- 让多个 Agent 进行讨论、辩论、思考、协作和对抗。

在此基础上，江湖 Online 需要进一步支持生产流程生成。

平台应让 LLM 综合以下两类知识：

### A. LLM 已有的通用社会与行业知识

利用 LLM 对现实社会中已有生产流程、岗位分工、行业惯例和质量控制方法的认知，例如：

- 产品需求与研发交付流程；
- 故障分析与处置流程；
- 数据分析与结论审核流程；
- 内容生产与事实核查流程；
- 安全审计与整改流程；
- 测试设计与质量评估流程；
- 其他与用户需求匹配的社会生产流程。

### B. 用户构建或传入的知识库

利用用户知识库中的组织专属内容，例如：

- 业务背景与目标；
- 组织结构和岗位职责；
- 现有制度、规范和标准作业流程；
- 项目资料和历史产物；
- 领域知识、术语和业务规则；
- 风险、合规和质量要求；
- 可用人员、Agent、工具和系统；
- 用户对最终产物的要求。

### C. 综合生成

LLM 不能只复述通用流程，也不能只根据用户资料机械拼接。平台应综合通用生产实践和用户专属知识，生成适合当前需求的：

1. 生产流程目标；
2. 流程节点及执行顺序；
3. 每个节点的输入；
4. 每个节点的活动和任务；
5. 每个节点需要的 Agent 角色；
6. Agent 的职责、知识、立场和关系；
7. 节点内部的协作与对抗方式；
8. 每个节点的正式步骤产物；
9. 步骤产物向后续节点的流转关系；
10. 节点完成条件和质量检查；
11. 人工确认或介入节点；
12. 最终产物及验收条件。

当前决策：

> 江湖 Online 的生产流程主要由 LLM 动态生成。生成时同时利用 LLM 掌握的社会生产流程知识和用户知识库内容。标准模板可以作为参考、约束或历史经验，但不是唯一生成入口。

## 5.2 知识不足时的处理原则

当前建议、尚待确认：

- 用户知识库优先表达组织事实和专属规则；
- LLM 通用知识用于补充社会上已有的生产流程和角色分工；
- 模型补充的内容应明确标记为建议或假设，不能伪装成用户组织事实；
- 当用户知识与通用实践冲突时，应展示冲突并请求确认；
- 缺少关键组织信息时，可以先生成流程草案，但不应直接宣称其为组织正式流程；
- 生成结果应说明哪些节点来自用户知识、哪些来自通用知识、哪些属于模型推导。

## 5.3 已确认：生成后直接执行并允许用户调整

江湖 Online 默认不要求用户在生成生产流程和 Agent 后先完成审批。

默认用户体验为：

```text
用户输入需求与知识
-> 平台生成生产流程和 Agent
-> 生产流程立即开始执行
-> 用户观察流程、Agent 和步骤产物
-> 用户按需调整生产流程或 Agent
-> 调整后的系统继续执行
-> 直至输出最终产物
```

已确认要求：

- 生产流程生成后可以直接开始执行；
- Agent 生成后可以直接参与生产步骤；
- 用户可以查看并调整生成的生产流程；
- 用户可以查看并调整生成的 Agent；
- “自动执行”和“用户可调整”必须同时成立；
- 平台不应要求普通用户先完成复杂配置才能看到运行结果。

由此推导出的产品方向：

- 生成结果应尽快可见并进入运行状态；
- 流程图、当前步骤、参与 Agent 和步骤产物应实时展示；
- 用户调整入口应存在于真实运行体验中，而不只是独立的后台配置页；
- 用户调整行为需要被记录，以便解释后续结果为何发生变化；
- 平台需要处理运行中修改对当前步骤、后续步骤和既有产物的影响。

## 5.4 已确认：运行中调整与版本控制

### 5.4.1 修改生效规则

当用户在运行过程中修改生产流程或 Agent 时：

1. 立即停止当前正在执行的节点；
2. 不再使用旧配置继续执行当前节点；
3. 将用户修改形成新的待确认配置；
4. 用户确认后才保存新配置；
5. 生产流程配置生成新的版本号；
6. 被修改的 Agent 配置生成新的版本号；
7. 保存后不自动继续执行；
8. 由用户点击“重新执行”启动节点或生产流程。

### 5.4.2 生产流程版本

生产流程需要独立的版本管理：

- 每次确认后的结构性修改产生新版本；
- 版本记录节点、顺序、依赖、输入、输出、参与 Agent 和执行规则；
- 一次运行必须绑定明确的生产流程版本；
- 历史运行仍引用当时使用的旧版本；
- 新版本不能覆盖或篡改历史版本；
- 用户可以查看不同版本之间的差异。

### 5.4.3 Agent 版本

Agent 需要独立的版本管理：

- 修改 Agent 的身份、职责、Prompt、模型、知识、工具、权限、记忆策略或行为规则后产生新版本；
- Agent 新版本经用户确认后保存；
- 一次节点执行必须记录实际使用的 Agent 版本；
- Agent 新版本不反向改变历史运行结果；
- 同一个生产流程版本中的不同运行可以绑定不同 Agent 版本；
- 用户可以查看 Agent 版本差异及其对结果的影响。

### 5.4.4 节点独立执行

生产流程中的每个节点都必须支持单独执行。

单独执行节点时：

- 可以继承上一个节点的产物输出作为当前输入；
- 用户可以选择符合要求的上游产物版本；
- 也可以由用户补充或替换当前节点输入；
- 节点执行绑定明确的流程版本、节点定义版本和 Agent 版本；
- 节点完成后生成新的步骤产物版本；
- 单独执行不应要求从整个生产流程的起点重新运行；
- 节点结果可以继续流转到后续节点。

### 5.4.5 步骤产物版本与来源

已经完成的步骤产物不得被直接删除或覆盖。

每个步骤产物至少需要记录：

- 产物 ID 和版本号；
- 所属生产流程及流程版本；
- 来源节点和节点执行记录；
- 使用的上游产物及其版本；
- 参与生成的 Agent 及其版本；
- 使用的知识、工具和关键输入；
- 创建时间和创建原因；
- 当前状态；
- 与上一版本的关系。

节点重新执行时创建新的产物版本，旧产物继续保留。后续节点必须明确引用其实际使用的产物版本，保证最终产物可以追溯到完整来源链。

## 5.5 已确认：生产流程采用有向任务图

江湖 Online 的生产流程不能只表达线性步骤，必须采用有向任务图表示节点、依赖、分支、并行、汇合和有限循环。

### 5.5.1 多上游输入

- 一个节点可以依赖一个或多个上游节点；
- 当前节点可以同时接收多个上游节点的产物；
- 每项输入必须记录具体的上游节点、产物 ID 和产物版本；
- 节点应定义必需输入和可选输入；
- 必需输入未满足时，节点不能被错误标记为可正常执行。

### 5.5.2 并行执行

- 没有相互依赖关系的多个节点可以并行执行；
- 并行节点可以由不同 Agent 团队执行；
- 每个并行节点独立记录状态、输入、产物、Agent 版本、耗时和错误；
- 单个并行节点失败时，应依据流程规则决定等待、重试、跳过、降级或终止其他分支。

### 5.5.3 条件分支

- 条件判断可以将生产流程导向不同分支；
- 判断依据可以来自结构化规则、步骤产物、Agent 评审结果或用户决定；
- 分支条件和实际选择结果必须被记录；
- LLM 作出的分支判断必须给出可查看的依据；
- 用户可以修改分支条件或人工选择分支。

### 5.5.4 汇合节点

- 汇合节点可以接收多个分支的步骤产物；
- 汇合节点可以综合、比较、筛选或裁决多个上游结果；
- 汇合结果必须保留对全部实际使用产物版本的引用；
- 某些分支缺失时，应按节点规则等待、降级执行或阻断，不能静默忽略。

### 5.5.5 对抗与裁判

- 对抗节点可以将同一方案或产物分发给多个 Agent；
- 多个 Agent 可以从不同立场进行攻击、质疑、复核或提出竞争方案；
- 对抗结果由评审 Agent、裁判 Agent、确定性规则或人工决定进行汇总；
- 对抗必须形成正式的质疑、缺陷、结论或修订要求；
- 裁判结果应引用参与评审的产物和证据。

### 5.5.6 有限返工循环

- 生产流程支持从评审、质检或裁判节点返回上游节点返工；
- 每个循环必须设置最大次数、退出条件或预算限制；
- 每轮返工产生新的节点执行记录和步骤产物版本；
- 达到循环上限后，流程必须进入通过、降级、阻断、失败或人工处理状态之一；
- 系统不得无限自动循环。

## 5.6 已确认：节点内部的多 Agent 组织策略

平台根据生产节点的目标、风险和产物类型，自动选择一种或组合多种多 Agent 执行策略，并允许用户查看和编辑。

支持的基础策略包括：

### 5.6.1 分工协作

- 不同 Agent 分别完成子任务；
- 子任务结果作为中间产物保存；
- 指定汇总 Agent 或汇合规则形成节点产物。

### 5.6.2 并行提案

- 多个 Agent 在尽量相互独立的上下文中生成候选方案；
- 平台保留每个候选方案及其来源；
- 后续通过比较、评分、投票或裁判选择和融合。

### 5.6.3 评审修订

- 一个或多个 Agent 负责产出；
- 其他 Agent 负责评审并提出问题；
- 产出 Agent 或修订 Agent 根据有效问题修改产物；
- 修订产生新的产物版本。

### 5.6.4 红蓝对抗

- 蓝方 Agent 提出方案、回答或防御；
- 红方 Agent 主动寻找漏洞、反例、风险和失败路径；
- 蓝方需要回应、修订或说明不接受攻击的理由；
- 对抗结论交给独立裁判 Agent 判断。

### 5.6.5 多轮辩论

- 多个具有不同立场的 Agent 围绕明确争议点进行有限轮次交锋；
- 每轮需要回应上一轮的具体主张；
- 辩论必须设置最大轮次和提前终止条件；
- 最终由独立裁判 Agent 汇总和裁决。

### 5.6.6 投票选择

- 多个 Agent 可以对候选方案进行评分或投票；
- 投票规则、权重和结果应公开记录；
- 投票不能取代必要的证据检查和独立裁判。

### 5.6.7 独立裁判

- 裁判 Agent 不参与被裁判产物的生成和修改；
- 裁判依据节点目标、验收标准、上游输入、候选产物和证据作出判断；
- 裁判输出评分、理由、证据引用和通过、返工、阻断等结论。

### 5.6.8 层级指挥

- 主管 Agent 拆解节点任务；
- 将子任务委派给不同专业 Agent；
- 检查子任务完成情况；
- 汇总形成候选节点产物；
- 最终质量仍由独立裁判 Agent 判断。

### 5.6.9 节点策略配置

需要使用多 Agent 的生产节点至少定义：

- 参与 Agent；
- Agent 角色、职责与立场；
- 协作和对抗策略；
- 每个 Agent 可见的信息范围；
- 消息、子任务和产物的传递方式；
- 最大交互、辩论和返工轮次；
- 候选结果的汇总方式；
- 如需要裁判，则定义独立裁判规则；
- 完成、失败、阻断和人工介入条件。

并非每个生产节点都必须采用多 Agent。平台应根据节点目标和复杂度选择合适的执行类型。

基础节点执行类型包括：

- 确定性节点：通过规则、程序或工具完成，不需要 Agent；
- 单 Agent 节点：由一个 Agent 独立完成明确任务；
- 多 Agent 协作节点：多个 Agent 分工或共同产出；
- 多 Agent 对抗节点：多个 Agent 进行质疑、攻防、竞争或辩论；
- 裁判节点：独立判断候选产物、争议或流程结果；
- 人工节点：等待用户输入、确认、选择或处理；
- 汇合节点：组合多个上游产物，可使用规则、Agent 或人工处理。

节点类型由平台在生成生产流程时推荐，用户可以调整。

是否使用多 Agent，应考虑：

- 节点是否包含多个专业领域；
- 单一 Agent 是否容易产生明显盲区；
- 是否存在需要比较的多个候选方案；
- 是否需要独立质疑、攻防或交叉验证；
- 节点错误对后续流程的影响；
- 多 Agent 带来的质量收益是否值得额外成本和时间。

简单的数据转换、格式整理、固定规则校验和明确工具调用，不应为了展示多 Agent 而强行配置多个 Agent。

## 5.6.10 已确认：拟人化 Agent

江湖 Online 中的 Agent 不只是隐藏在流程节点后的任务函数，而应参考 MiroFish，成为具有可辨识身份和行为特征的拟人化参与者。

拟人化 Agent 可以在生产流程中：

- 根据自己的身份和职责理解任务；
- 从自身专业、立场和掌握的知识出发提出观点；
- 主动与其他 Agent 讨论和交换信息；
- 对其他 Agent 的主张提出问题和质疑；
- 围绕争议点进行回应、反驳和辩论；
- 根据新证据修正观点；
- 尝试说服其他 Agent；
- 在规则允许时妥协、达成共识或保留异议；
- 共同创建、审查和修改步骤产物；
- 将无法解决的冲突提交给独立裁判或用户。

每个拟人化 Agent 至少可以具有：

- 名称和身份；
- 社会或组织角色；
- 专业背景和能力；
- 当前职责和任务目标；
- 立场、关注点和评价偏好；
- 可读取的知识范围；
- 可使用的工具；
- 与其他 Agent 的关系；
- 交流和行为风格；
- 当前上下文和记忆；
- 所属模型及模型配置版本；
- Agent 自身版本。

拟人化不能取代生产约束。Agent 的讨论、争辩和自由行动仍应服务于当前生产节点的目标和步骤产物，并受以下内容限制：

- 生产流程和节点边界；
- Agent 职责和权限；
- 可见知识范围；
- 时间、轮次和成本限制；
- 正式产物要求；
- 独立裁判和人工治理。

平台需要同时展示：

- Agent 之间发生了什么讨论和争议；
- 哪些观点最终影响了步骤产物；
- 哪些异议被接受、拒绝或提交裁决；
- 正式步骤产物与自由讨论之间的关系。

## 5.6.11 已确认：Agent 原型、运行实例和动态 Agent

江湖 Online 同时支持长期可复用的 Agent 原型和面向单次生产流程的 Agent 运行实例。

### Agent 原型

- 长期保存；
- 独立版本管理；
- 定义身份、专业背景、能力、职责、立场、知识权限、工具、模型和行为风格；
- 可以被多个生产流程和节点复用；
- 修改后产生新版本，不影响历史运行。

### Agent 运行实例

- 启动生产流程或节点时，根据指定 Agent 原型版本创建；
- 绑定本次流程、节点、任务和输入；
- 保存当前任务上下文、讨论状态和运行记忆；
- 与其他运行和其他用户的数据隔离；
- 运行结束后保留必要的执行记录和可追溯信息。

### 动态 Agent

- 当用户知识或任务需要当前 Agent 库中不存在的角色时，由平台临时生成；
- 可以立即作为运行实例参与生产流程；
- 运行后由用户决定是否保存为正式 Agent 原型；
- 保存为原型时需要用户确认其身份、能力、知识、工具和行为配置。

### 记忆写回

- 单次运行中的全部讨论不能自动成为 Agent 的长期事实；
- 候选经验、偏好或能力变化需要经过整理和用户确认；
- 经确认后才写入 Agent 原型的新版本或其长期记忆；
- 未经确认的运行记忆只属于对应运行实例；
- 历史运行记录和产物来源不得因记忆写回而被覆盖。

该设计参考 MiroFish 从知识图谱生成 Agent Profile、创建有状态角色并回写动态记忆的思路，但进一步增加可复用原型、运行实例隔离、版本管理和用户确认机制。

## 5.8 已确认：知识分层与访问范围

江湖 Online 的知识不能全部混合后提供给所有 Agent，必须按照用途和权限分层。

### 5.8.1 公共知识

公共知识是当前项目或生产流程中允许多个 Agent 共同使用的事实基础，例如：

- 用户输入的任务背景；
- 已确认的目标和约束；
- 组织公开制度和业务规则；
- 公共领域资料；
- 已发布的上游步骤产物；
- 用户明确声明所有参与者可见的信息。

公共知识可以被授权的多个 Agent 读取，但仍需保留来源和版本。

### 5.8.2 Agent 私有知识

Agent 私有知识只允许指定 Agent 或指定角色读取，例如：

- 专业领域知识；
- 角色专属材料；
- 私有任务说明；
- 只对红方、裁判或特定专家开放的信息；
- Agent 在当前任务中的私有工作记忆。

私有知识用于：

- 形成不同 Agent 的专业能力；
- 保持角色之间的认知差异；
- 构造必要的信息不对称；
- 避免所有 Agent 因共享完全相同的上下文而产生同质化回答。

Agent 不得在无权限时直接读取其他 Agent 的私有知识。需要共享时，应通过消息、正式产物或授权变更完成。

### 5.8.3 运行知识

运行知识是在本次生产流程执行过程中产生的信息，例如：

- 节点输入和步骤产物；
- Agent 提案、问题、回应和争议；
- 红队攻击和缺陷；
- 裁判结论；
- 用户介入和决定；
- 工具运行结果；
- 新出现的事实和假设；
- 当前流程状态。

运行知识必须绑定具体运行、流程版本、节点和来源。运行结束后，不自动成为跨流程长期知识。

### 5.8.4 分层组合与授权

每个生产节点应根据任务需要，为参与 Agent 组合授权：

```text
公共知识
+ 当前节点所需的上游产物
+ Agent 私有知识
+ 本次运行中允许读取的历史信息
```

平台生成 Agent 和生产流程时，应同时推荐知识访问范围，并允许用户调整。

### 5.8.5 知识使用原则

- 每项知识保留来源、版本和访问范围；
- Agent 输出应尽可能关联实际使用的知识或步骤产物；
- 公共知识更新后，不应静默改变正在运行的流程上下文；
- 私有知识不能因 Agent 讨论而被无意泄露；
- 运行知识写入公共知识或长期知识前，需要用户确认；
- 裁判只能读取裁判规则允许的知识，避免接触不应影响独立判断的信息。

## 5.9 已确认：混合知识库

江湖 Online 采用混合知识库，不将所有知识能力绑定到单一知识图谱。

混合知识库至少包含以下五个部分。

### 5.9.1 原始文档库

用于保存用户传入的完整原始资料。

要求：

- 保存原始文件和文件版本；
- 保存文件名称、类型、来源、上传者、时间和访问权限；
- 文档更新后保留历史版本；
- 文档解析结果不能覆盖原始文件；
- 支持从知识、步骤产物和 Agent 结论回到原文位置；
- 解析失败或未识别的内容应明确展示。

### 5.9.2 文本检索层

用于从原始资料中检索与当前任务相关的具体内容。

要求：

- 支持关键词检索；
- 支持向量或语义检索；
- 检索结果保留文档、版本和原文位置；
- 支持按知识范围和 Agent 权限过滤；
- Agent 使用检索内容时保留引用；
- 用户可以查看某项产物或结论实际引用了哪些文本片段。

### 5.9.3 知识图谱层

用于表达知识中的实体及其关系。

主要对象包括：

- 人物；
- 组织；
- 角色；
- 概念；
- 事件；
- 观点；
- 规则；
- 流程；
- 产物；
- 其他领域实体。

主要用途包括：

- 生成拟人化 Agent；
- 理解人物、组织和角色关系；
- 构建 Agent 江湖；
- 辅助生成生产流程和节点；
- 支持关系查询和上下文扩展；
- 保存运行过程中确认的新关系。

图谱中的实体和关系应尽可能关联原始文档证据。由模型推导但缺少直接来源的内容必须标记为推导或假设。

### 5.9.4 步骤产物库

用于保存生产流程每个节点产生的正式结构化产物。

要求：

- 产物独立于聊天记录保存；
- 支持类型、Schema、状态和版本管理；
- 记录上游输入、参与 Agent、流程版本、节点和来源；
- 允许后续节点选择明确的产物版本作为输入；
- 重新执行节点时产生新版本，不覆盖旧产物；
- 最终产物可以追溯到全部关键步骤产物。

### 5.9.5 记忆层

用于保存 Agent 实例和当前生产流程的运行状态。

包括：

- Agent 当前任务上下文；
- Agent 私有工作记忆；
- 节点执行状态；
- Agent 之间的讨论和消息；
- 当前争议和待解决问题；
- 用户介入记录；
- 运行检查点；
- 本次任务形成的候选经验。

记忆层内容不自动等同于组织知识，也不自动写入 Agent 原型。

### 5.9.6 五层协同原则

```text
原始文档库：保存完整事实来源
文本检索层：准确找到原文证据
知识图谱层：理解实体、关系和江湖结构
步骤产物库：承载正式生产结果及其流转
记忆层：维持 Agent 与流程的当前运行状态
```

知识图谱适合生成拟人化 Agent、理解关系和构建江湖；原文和文本检索适合提供准确证据。两者结合，避免图谱抽取遗漏后丢失原始信息。

## 5.10 已确认：开放的目标用户愿景

江湖 Online 的长期目标用户不局限于某一种职业或某一个行业。

平台希望让社会中具有不同身份、知识和目标的人，都能找到适合自己的使用方式，包括但不限于：

- 开发人员；
- 产品经理；
- 项目和研发负责人；
- 企业管理者；
- 运营人员；
- 数据分析人员；
- 咨询和研究人员；
- 教师和学生；
- 内容创作者；
- 客户和消费者；
- 社区组织者；
- 其他希望借助多 Agent 完成任务、讨论问题或构建生产流程的人。

长期产品表达为：

> 用户不需要先成为 Agent 开发者。无论用户来自什么职业或社会角色，都可以提供自己的需求和知识，由江湖 Online 帮助其构建适合场景的生产流程和拟人化 Agent，并通过协作、对抗和步骤产物流转完成目标。

### 5.10.1 共同用户需求

不同用户共享以下基础需求：

- 用自然语言描述目标；
- 提供或选择相关知识；
- 由平台生成合适的生产流程；
- 由平台生成或选择合适的 Agent；
- 立即看到流程运行；
- 查看 Agent 的讨论、争议和行动；
- 查看每一步形成的产物；
- 调整流程、Agent 和运行方式；
- 获得最终产物并追溯其形成过程；
- 将有效流程和 Agent 保存复用。

### 5.10.2 分层使用体验

为兼顾普通用户和专业用户，当前建议：

- 普通模式：用户只需描述需求和提供知识，平台自动生成并执行；
- 编辑模式：用户可以修改流程节点、Agent、知识范围和协作策略；
- 专业模式：开发人员可以配置模型、Prompt、工具、Schema、权限、版本和执行参数。

三种模式应使用同一套生产流程和 Agent 资产，而不是形成彼此割裂的产品。

### 5.10.3 范围控制原则

“服务各式各样的人”是产品愿景，不代表第一版本一次实现所有行业场景。

第一版本仍需要：

- 建立通用底层能力；
- 选择一个具有代表性的完整生产流程验证；
- 证明同一平台可以在不修改核心代码的情况下构建其他同类流程；
- 后续通过场景模板、知识包和 Agent 原型逐步扩展用户覆盖范围。

## 5.11 已确认：通用平台内核与场景包

江湖 Online 采用“通用平台内核 + 可复用场景包”的产品结构。

### 5.11.1 通用平台内核

所有用户和场景共享同一套基础能力：

- 混合知识库；
- 知识分层和权限；
- 基于需求的生产流程生成；
- 有向任务图执行；
- 拟人化 Agent 生成和运行；
- 单 Agent、多 Agent 协作与多 Agent 对抗；
- 独立裁判；
- 步骤产物及其流转；
- 流程、Agent 和产物版本管理；
- 运行观察、停止、调整和重新执行；
- 最终产物与来源追溯。

通用能力不能绑定到某个固定职业、行业或比赛案例。

### 5.11.2 场景包

场景包为特定领域或任务提供经过整理的可复用起点，例如：

- 软件需求与研发；
- 数据分析；
- 客户问题处理；
- 内容生产与事实核查；
- 学习与研究；
- 安全与质量评审；
- 用户自行创建的其他场景。

每个场景包可以包含：

- 典型用户目标；
- 参考生产流程；
- 流程节点及依赖；
- Agent 原型；
- 角色关系和协作/对抗策略；
- 步骤产物类型和 Schema；
- 质量标准和裁判规则；
- 示例知识；
- 可用工具；
- 示例任务和演示数据。

### 5.11.3 动态适配

场景包不是固定工作流。

平台应：

1. 理解用户当前需求；
2. 选择一个或多个相关场景包作为参考；
3. 结合 LLM 掌握的通用社会生产知识；
4. 结合用户混合知识库中的专属内容；
5. 动态生成或调整实际生产流程和 Agent；
6. 立即执行，并允许用户继续调整。

### 5.11.4 创建和复用

- 平台可以提供官方场景包；
- 用户可以创建自己的场景包；
- 已验证的生产流程、Agent 和评价规则可以保存为新场景包；
- 场景包需要版本管理；
- 场景包更新不能改变引用旧版本的历史运行；
- 后续可以支持场景包导入、导出和分享。

### 5.11.5 比赛场景

比赛选择的生产流作为第一个完整场景包和阶段性验收案例。

- 比赛逻辑必须通过通用平台能力配置和生成；
- 不能硬编码为系统唯一流程；
- 比赛结束后，通用内核仍能构建其他生产流程；
- 比赛场景包用于证明平台具有真实运行、协作、对抗、产物流转和效果提升能力。

## 5.12 已确认：大江湖与小江湖

江湖 Online 需要规划两种江湖规模。

### 小江湖

- 只生成完成目标所必需的 Agent；
- 以最小必要角色、关系和互动为原则；
- 优先保证效率、成本、职责清晰和快速交付；
- 简单节点不强行使用多个 Agent；
- 必要节点仍可使用协作、对抗和独立裁判；
- 作为 MVP 默认模式。

### 大江湖

- 在必要角色基础上增加更多 Agent；
- 引入更多专业背景、利益相关方、立场和边缘视角；
- 支持更丰富的关系、并行提案、讨论、辩论、投票和群体互动；
- 可用于复杂决策、高风险评审、研究推演和认知多样性要求较高的任务；
- 可以只扩展指定节点，不要求每个节点都有大量 Agent；
- 仍然通过正式步骤产物完成节点流转；
- 必须受 Agent 数量、轮次、时间、Token、成本和终止条件约束。

共同原则：

- “大”与“小”不使用固定人数定义；
- 江湖规模可以由用户选择或由系统根据任务推荐；
- 新增 Agent 必须具有可解释作用；
- 修改江湖规模属于结构性修改，需要停止当前节点、保存新版本并重新执行；
- 后续应支持比较大江湖和小江湖的质量、风险、耗时和成本差异。

## 6.1 已确认：首个比赛生产流

首个完整比赛场景包选择：

> **产品需求到可开发方案**

### 6.1.1 场景目标

用户可以提供任意产品的原始想法、背景知识、约束和期望结果。江湖 Online 自动生成适合当前需求的生产流程和 Agent 团队，通过多步骤协作、评审、对抗、修订和独立裁判，最终形成可供产品设计和研发实施使用的完整方案。

该场景包定义的是一种通用生产能力，不绑定任何具体产品。

- PRD 不预先指定被分析产品；
- 系统不内置固定产品需求；
- 被分析产品由用户在每次运行时输入；
- 平台根据不同产品需求动态调整节点、Agent 和步骤产物；
- 比赛演示时使用的产品材料只是临时运行数据；
- 更换产品材料后，不修改核心代码即可重新生成和运行。

### 6.1.2 参考生产流程

以下流程是场景包参考结构，实际运行时允许 LLM 根据用户需求和知识动态调整：

```text
原始需求与知识接入
-> 需求澄清
-> 用户与价值分析
-> 产品方案
-> 技术可行性分析
-> 多 Agent 交叉评审
-> 红队攻击
-> 修订
-> 独立裁判
-> 输出完整 PRD 和实施建议
```

### 6.1.3 可使用的节点结构

- 需求澄清节点：单 Agent 或多 Agent 协作；
- 用户与价值分析节点：用户研究、业务和产品 Agent 协作；
- 产品方案节点：产品 Agent 生成方案；
- 技术可行性节点：架构、开发或安全 Agent 并行分析；
- 交叉评审节点：产品和技术 Agent 互相质疑；
- 红队攻击节点：多个不同攻击立场的 Agent 寻找缺陷；
- 修订节点：根据成立的缺陷产生新版本产物；
- 独立裁判节点：使用独立裁判 Agent 进行终审；
- 最终汇合节点：形成标准 PRD 和实施建议。

### 6.1.4 主要步骤产物

- 原始需求记录；
- 需求澄清结果；
- 用户、问题和价值分析；
- 产品范围和功能方案；
- 用户流程和业务规则；
- 技术可行性及约束建议；
- 交叉评审意见；
- 红队缺陷清单；
- 缺陷处置和修订记录；
- 独立裁判结果；
- 标准 PRD；
- 实施建议。

### 6.1.5 比赛验证价值

该场景适合验证：

- 不同专业 Agent 的明确分工；
- 并行分析与多产物汇合；
- Agent 之间的讨论和争辩；
- 红队主动发现遗漏、矛盾和风险；
- 修订是否真正解决问题；
- 独立裁判是否提升最终结果可信度；
- 步骤产物是否能够可靠流转；
- 多 Agent 相比单 Agent是否提高需求完整性、风险发现率和最终产物质量。

### 6.1.6 非目标

当前不需要在产品需求阶段确定比赛演示将使用哪个具体产品。

具体演示材料可以在比赛准备或系统验证阶段选择，不应成为平台需求、场景包结构或核心代码的一部分。

## 6.2 已确认：最低启动输入

江湖 Online 应尽量降低创建生产流程的使用门槛。

### 6.2.1 必需输入

用户最低只需要输入一句自然语言需求，即可启动生产流程生成和执行。

例如：

```text
帮我把这个产品想法整理成可开发的产品方案。
```

系统不应强制用户先理解或配置：

- Agent；
- Prompt；
- 模型参数；
- 流程节点；
- 产物 Schema；
- 知识图谱；
- 协作与对抗策略。

### 6.2.2 可选输入

用户可以选择提供：

- 上传文件；
- 选择已有知识库；
- 补充任务背景；
- 指定目标用户；
- 描述业务目标；
- 提供组织规则和限制；
- 指定期望最终产物；
- 设置时间、成本或质量偏好；
- 选择参考场景包；
- 指定必须或禁止使用的 Agent、模型和工具。

### 6.2.3 信息不足时

信息不足不默认阻止生产流程启动。

平台可以：

1. 利用 LLM 掌握的通用社会和行业知识补全生产流程；
2. 生成合理但明确标记的假设；
3. 基于现有信息立即生成 Agent 和生产流程；
4. 直接开始执行；
5. 在运行过程中向用户展示假设和不确定项；
6. 允许用户补充信息、修改假设或调整流程；
7. 按已确认的变更规则停止当前节点、保存新版本并由用户重新执行。

### 6.2.4 假设管理

- 模型补全内容不能伪装成用户事实；
- 每项重要假设应说明原因和可能影响；
- 步骤产物应能够引用其依赖的假设；
- 用户可以确认、修改或否决假设；
- 假设变化可能导致流程、Agent 或步骤产物产生新版本；
- 最终产物应列出仍未被确认的重要假设。

## 6.3 已确认：实时生产与江湖观察工作台

用户提交需求后，默认进入实时生产工作台，而不是只看到聊天框、复杂配置表单或最终结果页。

页面整体风格参考 MiroFish：

- 简洁；
- 清晰；
- 具有沉浸式观察感；
- 重点突出 Agent、关系、事件和生产过程；
- 避免在首屏堆叠过多专业配置项；
- 普通用户能够快速理解当前发生了什么。

### 6.3.1 生产流程图

工作台展示自动生成的有向任务图：

- 节点及其依赖关系；
- 并行、分支、汇合和循环；
- 当前执行节点；
- 已完成、等待、停止、失败和待重新执行状态；
- 每个节点的执行类型；
- 参与节点的 Agent；
- 节点输入和步骤产物；
- 节点裁判或人工介入状态。

用户可以点击节点查看详细内容，也可以修改节点、依赖、Agent 和执行策略。

### 6.3.2 知识图谱

工作台必须提供知识图谱展示，至少能够呈现：

- 人物；
- Agent；
- 组织；
- 角色；
- 概念；
- 事件；
- 观点；
- 规则；
- 流程；
- 步骤产物；
- 实体之间的关系。

知识图谱应支持：

- 查看实体和关系详情；
- 查看知识来源和原文引用；
- 区分原始事实、模型推导、假设和运行中新形成的信息；
- 查看 Agent 与知识、角色和产物的关系；
- 从知识图谱跳转到对应 Agent、流程节点或步骤产物；
- 随运行过程更新已确认的新实体和关系。

知识图谱不是单独的装饰页面，应与生产流程图、Agent 和产物流转相互关联。

### 6.3.3 Agent 江湖

工作台展示当前生产流程中的拟人化 Agent：

- Agent 名称、头像或视觉标识；
- 身份、职责和立场；
- 当前状态和任务；
- 与其他 Agent 的关系；
- 当前所在节点；
- 正在思考、讨论、等待、攻击、回应、修订或裁判等可观察行为；
- 所使用的 Agent 和模型版本。

### 6.3.4 多 Agent 过程展示

用户不能只能查看最终产物。系统必须展示 Agent 在生产过程中的可观察输出，包括：

- 独立观点；
- 子任务结果；
- Agent 之间的讨论；
- 追问与回答；
- 辩论与反驳；
- 分工协作；
- 红队攻击；
- 蓝方回应；
- 评审意见；
- 冲突与分歧；
- 投票或评分；
- 独立裁判结论；
- 产物修改和版本变化。

用户应能够分别查看：

- 某个生产节点中发生的全部 Agent 互动；
- 某个 Agent 在整个运行中的行为和输出；
- 某次协作、对抗或辩论的完整过程；
- 某个步骤产物受到哪些 Agent 观点和决定影响。

### 6.3.5 正式输出与可观察过程

平台需要区分：

- 可观察的 Agent 发言、讨论和行为；
- 用于节点流转的正式步骤产物；
- 裁判、用户或规则形成的正式决定。

讨论内容不能自动等同于正式产物，但用户应能从正式产物追溯到影响其形成的讨论、证据和 Agent。

### 6.3.6 运行控制

工作台至少支持：

- 停止当前节点；
- 查看运行状态；
- 修改生产流程；
- 修改 Agent；
- 确认并保存新版本；
- 点击重新执行；
- 选择上游产物版本；
- 单独执行节点；
- 查看历史节点执行和产物版本。

## 6.4 已确认：三个联动主视图

江湖 Online 工作台采用三个相互联动的主视图，避免将生产流程、知识图谱、Agent 互动和产物全部挤在同一个画布中。

### 6.4.1 生产视图

生产视图以有向任务图为中心，主要回答：

> 当前生产任务做到哪里，接下来要做什么？

主要内容：

- 生产流程节点和依赖；
- 当前节点和整体进度；
- 分支、并行、汇合和返工循环；
- 节点状态；
- 节点参与 Agent；
- 节点输入和步骤产物；
- 当前节点的 Agent 讨论、协作和对抗；
- 节点运行控制和编辑入口。

### 6.4.2 江湖视图

江湖视图以知识、Agent 和关系图谱为中心，主要回答：

> 江湖中有哪些参与者、知识和关系，它们正在如何互动？

主要内容：

- 知识实体和关系；
- Agent 身份、立场和关系；
- Agent 与知识的连接；
- Agent 与生产节点和产物的连接；
- 选中 Agent 的当前行为和历史输出；
- 讨论、辩论、协作和对抗关系；
- 运行中新形成的事实、观点和关系。

### 6.4.3 产物视图

产物视图以步骤产物或最终产物为中心，主要回答：

> 当前结果是什么，它是如何形成的？

主要内容：

- 产物正文或结构化内容；
- 产物版本；
- 上游产物和知识来源；
- 参与生成和修改的 Agent；
- 相关讨论、争议和裁决；
- 红队缺陷和修订记录；
- 产物状态和下游引用；
- 不同版本之间的差异。

### 6.4.4 视图联动

三个视图使用同一运行上下文。

- 在生产视图选择节点，江湖视图定位相关 Agent 和知识，产物视图定位节点产物；
- 在江湖视图选择 Agent，生产视图定位其参与的节点，产物视图列出其影响的产物；
- 在江湖视图选择知识实体，生产和产物视图显示其被使用的位置；
- 在产物视图选择证据、Agent 或上游产物，可以跳转到相应视图；
- 视图切换后保留用户当前选择和运行位置。

### 6.4.5 统一状态区域

三个视图共享统一的顶部或全局状态区域，至少展示：

- 当前生产流程；
- 流程版本；
- 运行状态；
- 当前节点；
- 整体进度；
- 当前成本和时间；
- 停止、编辑和重新执行入口；
- 待用户处理的事件。

## 6.5 已确认：Agent 可观察输出与私有思维边界

江湖 Online 应展示 Agent 在生产流程中主动发布的可观察信息，但不展示模型私有思维链。

### 6.5.1 应展示的信息

- Agent 当前观点；
- 支持观点的理由摘要；
- 使用的知识和证据引用；
- 对其他 Agent 的提问；
- 对问题和攻击的回应；
- 提案、建议和候选方案；
- 质疑、反驳和红队攻击；
- 修订说明；
- 当前行动计划和任务状态；
- 工具调用和结果摘要；
- 置信度；
- 假设和未解决问题；
- 影响正式步骤产物的关键决定。

### 6.5.2 不展示的信息

- 模型私有思维链；
- 未经过整理的内部逐字推理；
- 与用户任务无关的隐藏上下文；
- Agent 无权公开的私有知识；
- 凭据、密钥和其他敏感字段；
- 仅用于模型运行的底层控制信息。

### 6.5.3 展示原则

- 可观察输出应能够让用户理解 Agent 为什么采取某项行动；
- 发言和事件应标记 Agent、时间、节点和类型；
- 讨论可以按协作、对抗、裁判、工具和系统事件筛选；
- 正式产物应引用影响其形成的关键可观察输出；
- 可观察摘要不能伪装成模型完整内部推理；
- Agent 私有知识只在权限允许时通过正式消息或产物共享。

## 6.6 已确认：用户作为江湖参与者

江湖 Online 中的用户不仅是流程发起者和观察者，也可以直接成为江湖中的参与者。

### 6.6.1 用户参与方式

用户可以：

- 只观察生产流程和 Agent 江湖；
- 向单个 Agent 提问；
- 向多个 Agent 发送同一问题；
- 加入当前节点的讨论或辩论；
- 提供新事实、知识或证据；
- 表达观点、质疑或反驳；
- 修改目标、约束和验收标准；
- 要求某个节点返工；
- 接管某个生产节点；
- 作为指定角色参与一段或完整生产流程；
- 担任评审者或裁判。

### 6.6.2 非正式介入

非正式介入用于讨论和探索，例如：

- 追问某个 Agent；
- 提供建议；
- 要求解释；
- 对某个观点表示支持或反对；
- 向当前讨论注入新信息。

非正式介入不会自动修改正式步骤产物、生产流程或 Agent 配置。

### 6.6.3 正式介入

正式介入会影响流程、配置、产物或决定，例如：

- 确认或否决假设；
- 修改生产流程；
- 修改 Agent；
- 改变知识权限；
- 确认新配置版本；
- 要求停止和重新执行；
- 接受或驳回缺陷；
- 作出裁判结论；
- 批准或阻断最终产物。

正式介入必须记录用户、时间、对象、内容、原因和影响范围。

### 6.6.4 用户担任裁判

用户可以在节点、对抗、候选方案选择、质量门或最终验收中担任裁判。

用户裁判可以：

- 查看候选产物；
- 查看 Agent 的公开讨论和证据；
- 向参与 Agent 追问；
- 接受或驳回攻击与评审意见；
- 选择候选方案；
- 要求修订或重新执行；
- 作出通过、返工、阻断等正式结论。

用户裁判结果必须作为正式决定保存，并与当时使用的流程版本、Agent 版本、产物版本、验收标准和证据关联。

### 6.6.5 用户身份与权限

用户加入江湖时应具有明确身份和权限，例如：

- 发起者；
- 观察者；
- 领域专家；
- 流程负责人；
- 节点执行者；
- 评审者；
- 裁判；
- 最终批准者。

用户身份决定其可以查看、修改、裁决或批准的内容。

## 6.7 已确认：默认自治与用户最高决定权

### 6.7.1 默认自治运行

江湖 Online 的生产流程默认不依赖用户逐步确认。

即使用户在启动后完全不参与，系统也应能够：

1. 根据用户需求和知识生成生产流程；
2. 生成或选择 Agent；
3. 执行各个节点；
4. 完成单 Agent、多 Agent 协作和多 Agent 对抗；
5. 使用独立裁判处理需要裁决的内容；
6. 形成步骤产物并继续流转；
7. 处理分支、汇合和有限返工；
8. 运行到明确的完成、失败或阻断状态；
9. 输出最终产物和完整过程记录。

流程中不应默认设置“每一步等待用户确认”的阻塞点。

### 6.7.2 用户最高决定权

用户拥有生产流程中的最高决定权。

- 用户可以接受或推翻 AI 裁判结论；
- 用户可以修改目标、约束、流程、Agent 和知识；
- 用户可以停止、重新执行或终止流程；
- 用户可以接管节点；
- 用户可以作出最终通过、返工或阻断决定；
- 用户决定不能被 Agent 自动覆盖。

当用户推翻 AI 裁判或改变正式决定时：

- 保留 AI 原结论；
- 保存用户最终决定；
- 记录用户提供的理由或说明；
- 标记对流程、节点和产物的影响；
- 不覆盖或删除历史记录。

### 6.7.3 随时加入

用户可以在流程运行期间随时：

- 加入多 Agent 讨论；
- 打断当前讨论；
- 向一个或多个 Agent 补充说明；
- 提供新事实、材料或证据；
- 回答 Agent 的问题；
- 对争议表达意见；
- 临时担任裁判；
- 要求调整或重新执行。

### 6.7.4 人工参与原则

```text
默认：系统自治运行到结束
可选：用户随时观察或加入
最高权力：用户可以覆盖 AI 决定
审计要求：AI 原结论与用户决定同时保留
```

人工参与是用户的权利，不是流程完成的默认前置条件。

## 6.8 已确认：讨论介入与结构性介入

用户在运行期间的介入分为讨论介入和结构性介入，两者使用不同的生效规则。

### 6.8.1 讨论介入

讨论介入包括：

- 向当前讨论补充一句说明；
- 回答 Agent 的问题；
- 提供观点、建议或提醒；
- 对某个 Agent 进行追问；
- 要求 Agent 解释或继续讨论；
- 在不改变正式任务定义的情况下提供补充上下文。

处理规则：

1. 暂停当前对话轮次或等待当前安全输出点；
2. 将用户内容作为正式可观察消息加入当前讨论；
3. 相关 Agent 接收用户补充；
4. Agent 根据新信息继续讨论和执行；
5. 不生成生产流程新版本；
6. 不生成 Agent 新版本；
7. 不要求用户手动点击重新执行；
8. 用户消息及其影响进入运行记录。

讨论介入可能影响当前步骤产物，但产物仍按正常产物版本规则保存。

### 6.8.2 结构性介入

结构性介入包括：

- 修改生产流程节点或依赖；
- 修改节点目标、输入、输出或完成条件；
- 修改 Agent 身份、职责、模型、Prompt、工具或权限；
- 修改知识访问范围；
- 替换正式节点输入；
- 修改协作、对抗或裁判策略；
- 修改关键业务约束或验收标准。

处理规则：

1. 立即停止当前节点；
2. 保留停止前的运行记录和未完成状态；
3. 形成新的待确认配置；
4. 用户确认后保存相应新版本；
5. 不自动继续执行；
6. 由用户点击重新执行；
7. 新执行绑定新流程、Agent 或输入版本；
8. 历史配置和产物不被覆盖。

### 6.8.3 介入类型判断

平台应根据用户行为自动判断介入类型，并明确告知用户其影响。

当系统无法可靠判断时：

- 默认按影响较小的讨论介入处理；
- 如果内容将改变正式配置或输入，应提示用户确认转换为结构性介入；
- 不得在用户不知情的情况下自动创建配置新版本或停止整个流程。

## 6.9 已确认：MVP 暂不要求外部工具接入

MVP 不需要实现复杂的外部工具和真实业务系统接入。

暂不作为 MVP 必需功能：

- MCP Server 接入；
- 任意 HTTP API 注册；
- 企业数据库连接；
- 代码仓库操作；
- 第三方 SaaS 操作；
- 外部系统写入；
- 高风险工具审批体系；
- 完整工具市场或工具注册中心。

MVP 可以只提供完成核心流程所需的基础内部能力，例如：

- 读取用户输入；
- 读取混合知识库；
- 检索原始文档；
- 查询知识图谱；
- 读取上游步骤产物；
- 保存步骤产物；
- 调用用户已接入的 LLM；
- 生成最终文档。

MVP 核心验证重点是：

```text
知识驱动生成拟人化 Agent
+ 需求驱动生成标准生产流程
+ 多 Agent 协作、讨论和对抗
+ 独立裁判
+ 步骤产物流转
+ 用户观察与随时介入
+ 版本和来源追溯
+ 最终产物输出
```

外部工具生态可以在核心生产闭环得到验证后作为后续版本能力扩展。

## 6.10 已确认：MVP 混合知识库边界

MVP 保留混合知识库的五层产品概念，但采用轻量实现。

### 6.10.1 原始文档库

MVP 必须支持：

- 用户上传基础文档；
- 保存原始文件；
- 解析文档内容；
- 保存文件版本；
- 记录来源；
- 从知识、Agent 输出和产物返回原文引用。

复杂数据源连接暂不要求。

### 6.10.2 文本检索层

MVP 支持：

- 基础关键词检索；
- 基础向量或语义检索；
- 按当前知识范围过滤；
- 返回文档来源和内容片段。

复杂检索编排、重排模型和企业搜索集成暂不要求。

### 6.10.3 知识图谱层

MVP 支持：

- 从用户资料中自动抽取基础实体和关系；
- 展示人物、组织、角色、概念、规则和流程等核心实体；
- 将实体关联到原始文档来源；
- 将 Agent 与其来源实体、知识和关系连接；
- 在江湖视图中可视化。

复杂人工图谱编辑、图谱治理、跨数据源融合和高级推理暂不要求。

### 6.10.4 步骤产物库

步骤产物库是 MVP 核心能力，必须支持：

- 保存节点正式产物；
- 产物类型和结构；
- 版本管理；
- 上游产物引用；
- 节点和 Agent 来源；
- 后续节点选择和继承；
- 重新执行产生新版本；
- 最终产物的来源追溯。

### 6.10.5 记忆层

MVP 支持：

- 单次运行状态；
- Agent 实例当前任务上下文；
- Agent 私有工作记忆；
- 节点内讨论和事件；
- 用户介入记录；
- 运行结束后的历史查看。

复杂跨任务长期学习、自动经验沉淀和跨场景记忆复用暂不要求。

### 6.10.6 MVP 优先级

```text
最高优先：步骤产物版本与流转
高优先：原始文档与证据引用
高优先：运行和 Agent 实例记忆
中优先：基础文本检索
中优先：基础知识图谱生成与展示
后续版本：复杂图谱治理和跨任务长期学习
```

## 6.11 已确认：MVP 用户与项目模型沿用 MiroFish

经核对 MiroFish 当前源码，MiroFish 采用本地单用户、项目制运行方式：

- 没有登录和注册；
- 没有团队 Workspace；
- 没有成员邀请；
- 没有复杂用户角色和组织权限；
- 通过项目 ID 管理资料和图谱；
- 通过模拟 ID 管理运行；
- 通过报告 ID 管理报告和后续交互；
- 项目数据在服务端按项目目录保存。

江湖 Online MVP 沿用这一简化设定。

### 6.11.1 MVP 包含

- 本地单用户使用；
- 创建多个项目；
- 每个项目拥有独立需求、知识、图谱、流程、Agent、运行和产物；
- 项目历史列表；
- 通过项目进入生产流程和历史运行；
- 项目之间基础数据隔离；
- Agent 公共知识和私有知识范围；
- 生产流程、Agent 和步骤产物版本管理。

### 6.11.2 MVP 不包含

- 用户注册和登录；
- 多用户同时协作；
- 团队和组织管理；
- Workspace 成员；
- 邀请和分享权限；
- 复杂 RBAC；
- 企业单点登录；
- 租户级数据隔离。

### 6.11.3 后续扩展

数据模型可以预留用户、组织或 Workspace 归属字段，但 MVP 页面和运行流程不依赖这些能力。

该选择只沿用 MiroFish 的简化用户与项目模型，不代表江湖 Online 的长期产品永远限定为单用户。

## 6.12 已确认：MVP 本地部署优先

江湖 Online MVP 优先支持本地安装和运行。

### 6.12.1 本地运行要求

- 区分本地保存的数据和发送给外部服务的数据；

云端托管、账号体系、多租户和团队协作可在 MVP 核心闭环验证后继续规划。

### 验证目标三：安全算力 2.0 需求交付评审

- 输出证据、受影响需求、交付节点、风险等级和后续验证动作；
- 如果材料不包含足够证据，不得为了命中预期结论而虚构问题。

## 5.7 已确认：多 LLM 接入与独立裁判模型

### 5.7.1 多 LLM 接入

江湖 Online 支持用户接入一个或多个 LLM。

每个 LLM 配置至少应包含：

- 供应商和模型标识；
- 连接方式和凭据引用；
- 用户设置的能力等级；
- 可选的能力标签；
- 上下文长度、成本和速率限制；
- 是否允许用于普通 Agent；
- 是否允许用于独立裁判 Agent。

平台不能假设某个固定供应商或固定模型永远最强。“最高能力模型”以用户配置的能力等级为准。

### 5.7.2 独立裁判模型选择

- 当用户接入多个 LLM 时，平台默认选择用户设置的最高能力 LLM，作为独立裁判 Agent 的模型；
- 用户可以查看并调整裁判所使用的模型配置；
- 裁判运行必须记录实际使用的模型及模型配置版本；
- 更换裁判模型后重新裁判，应产生新的裁判结果版本，不能覆盖旧结果。

### 5.7.3 只有一个 LLM 时

用户只接入一个 LLM 不影响平台运行，但仍必须创建独立裁判 Agent。

即使裁判和其他 Agent 使用同一个底层 LLM，独立裁判也必须满足：

- 使用独立 Agent 身份；
- 使用独立系统指令和职责；
- 使用独立运行上下文；
- 不参与候选产物的生成和修订；
- 不读取不应影响裁决的生成过程信息；
- 只依据允许的输入、正式产物、验收标准和证据进行裁决；
- 独立保存裁判结果和执行记录。

### 5.7.4 强制独立裁判原则

江湖 Online 必须具备独立裁判能力，但不要求每个生产节点都配置独立裁判。

- 产出 Agent 不能对自己的产物作最终批准；
- 红方或评审方不能直接充当最终裁判；
- 投票结果不能自动代替独立裁判结论；
- 裁判不能直接修改被裁判产物；
- 裁判发现问题时，应返回明确的返工要求或阻断理由；
- 最终通过结论必须可追溯到裁判 Agent、模型版本、验收标准和证据。

独立裁判优先用于：

- 多 Agent 对抗后的争议裁决；
- 多个候选方案的选择；
- 重要步骤产物的质量门；
- 高风险决策；
- 最终产物的终审。

普通节点是否配置独立裁判，由平台根据风险和流程需要推荐，并允许用户调整。

## 6. 比赛课题

比赛课题：

> 选定一个生产流，设计多个 Agent 进行协作与对抗。

课题关注的核心问题：

- 真实生产流程通常涉及多个角色协同；
- 单一 Agent 难以同时兼顾效率、质量、风险和约束；
- 多个角色 Agent 应围绕统一目标分工协作；
- 应通过质疑、审查、校验、攻防或反驳发现问题并提升结果质量。

推荐生产流方向包括：

1. 需求到交付生产流；
2. 问题定位与处置生产流；
3. 数据分析生产流；
4. 安全与质量评审生产流；
5. 测试设计生产流。

最终选择哪一个生产流，尚未确认。

## 7. 比赛硬性要求

比赛成果至少需要满足：

- 至少包含 3 个不同角色的 Agent；
- 每个 Agent 有清晰的职责边界；
- Agent 之间有明确的信息传递、协作或任务流转机制；
- 至少包含一个对抗或质疑环节；
- 最终输出应比单 Agent 方案更完整、更可靠；
- 系统必须可运行、可演示，不能只提供流程图或设计文档；
- 支持真实输入输出，不能只有概念设计；
- 至少展示 1 个完整业务生产流；
- 能说明业务价值、准确率、质量或效率提升。

## 8. 比赛进阶要求

- 支持 Agent 之间多轮协商，而不是一次性交接；
- 支持多个 Agent 结论不一致时的冲突处理或仲裁；
- 支持结果评分或置信度评估；
- 支持人工介入节点和关键决策确认；
- 支持真实数据、真实接口或真实业务规则。

## 9. 比赛最终交付物

必须或建议形成：

1. 可运行 Demo，以及演示地址或本地运行说明；
2. 代码仓库或核心代码说明；
3. README，包括系统架构、运行方式、依赖环境和使用示例；
4. 至少 1 个完整业务场景演示；
5. 单 Agent 与多 Agent 协作/对抗的效果对比；
6. 效能、准确率或质量提升说明；
7. Agent 角色说明与协作流程图；
8. 可选的演示视频、测试报告和部署说明。

## 10. 明确不接受的交付状态

- 只有 PPT，没有可运行成果；
- 只有提示词，没有系统能力；
- 只有概念设计，没有真实输入输出；
- 只能运行一个固定样例，无法泛化到同类场景；
- 无法说明业务价值、准确率或效率提升。
