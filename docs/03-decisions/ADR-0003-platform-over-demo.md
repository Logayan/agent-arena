# ADR-0003：Agent Arena 定位为多 Agent 平台而非单场景 Demo

- 状态：已接受
- 日期：2026-07-24

## 背景

当前 MVP 使用“智能需求评审示例”展示多 Agent 协作、红队攻击、修订和裁判流程。

该示例能够满足课题的纵向演示需求，但用户的长期目标是建立自己的多 Agent 协作与对抗体系，覆盖员工、研发、客户和其他组织场景。

如果继续围绕固定需求评审流程扩展，Agent、知识、事件和 Client 都会与单一场景强耦合，未来难以复用。

## 决策

Agent Arena 的正式产品定位调整为：

> 面向组织场景的多 Agent 社会操作系统与工作流工厂。

“智能需求评审”保留为首个场景模板和课题交付案例，不再作为平台首页的固定业务边界。

## 架构影响

平台需要引入以下一级领域：

- `Workspace`：组织级数据与权限边界
- `KnowledgeSpace`：知识和证据空间
- `AgentBlueprint`：可复用 Agent 蓝图
- `SocietyTemplate`：组织和治理模板
- `WorkflowTemplate`：可复用工作流模板
- `Scenario`：用户提交的具体业务场景
- `WorkflowDefinition`：根据场景生成的运行定义
- `Run`：一次执行
- `EvaluationSuite`：质量和效果评估

现有 `Run`、`Agent` 和 `Event` 模型将保留，但需要从固定演示数据中解耦。

## Client 影响

正式入口应从自动加载 `/api/demo` 调整为：

```text
工作区
-> 新建场景
-> 连接知识
-> 生成/配置 Agent 社会
-> 生成/编辑工作流
-> 运行
-> 评估与沉淀
```

固定 Demo 作为“示例模板”进入模板库。

## 实施影响

下一阶段优先级调整为：

1. 工作区与场景创建
2. Agent 蓝图和 Agent 配置
3. 知识空间
4. 工作流定义和编排
5. 真实 Agent Worker
6. 对抗、裁判与评估
7. 模板库和历史优化

## 风险

- 平台范围显著扩大，必须分阶段交付。
- 过早追求完全自动生成会降低可控性。
- 不同场景的评估标准差异很大。
- 组织知识和客户数据需要严格隔离。

## 缓解方式

- 使用场景模板约束早期生成。
- 将自动生成结果作为草案，运行前由用户确认。
- 先支持有限场景族，再扩展通用性。
- 通过版本化 Schema 和插件接口保持核心稳定。
