## 当前 GPT API 配置真实探针

用户明确授权使用主数据库当前 `openai-responses / gpt-5.6-sol` 配置继续 G1。采集器增加 `--real-model-source active-database`，以只读 SQLite 查询和本地密钥解密取得 active 配置；Token 不进入命令行、控制台或归档正文。

无费用语法与回归检查通过后，执行了一次受控真实探针。结果序列为：第一次模型请求 200，模型调用 `read`，OpenClaw 返回工具结果，第二次模型请求 401，最终以认证原因失败。没有创建目标交付文件，也没有自动重试。

结论：当前 GPT 配置能够完成首轮请求，但不能完成多轮工具闭环。该问题归类为 Provider 续轮认证或 OpenAI Responses 网关兼容阻塞。采集器已增加 `provider_auth` 分类和失败时流式动作归档；因不应篡改原始证据，已生成 manifest 保留原来的 `runtime_failure/failed`，正式解释记录在基线报告中。

随后只读检查本机 OpenClaw transport 实现：每个 Responses 回合均从同一 `options.apiKey` 创建 Client，本地代码没有显示第二轮故意省略认证。下一步若要定位 401，需要模型网关服务端日志，而不是继续盲目调用模型。

用户要求修改后，进一步用相同数据库配置直接请求 `/v1/responses`，完全绕过 OpenClaw。最小函数工具请求首轮即返回 401，未形成任何 SSE Responses 事件。这说明当前 GPT 网关凭据或服务端认证状态本身不可用/不稳定，不能靠修改 OpenClaw 工具消息解决。

已保留仓库内可控修正：active 数据库只读模型加载、`provider_auth` 阻塞分类、失败流式动作归档和不重试 401。外部网关 Token 更新或服务端鉴权修复需要新的有效配置或网关管理权限。

为防止采集器修改本身回退，新增两项无网络测试：验证 active SQLite 模型配置可解密读取且数据库字节不变；验证 401、余额不足和 Runtime 故障分类。Runtime 合同目录最新结果为 `8 passed`。
