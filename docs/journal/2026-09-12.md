## Artifact 原始字节哈希断链与可审计修复

返工审计随后发现：数据库中的 Artifact 登记哈希按模型返回字符串的 UTF-8 原始字节计算，但 Windows 上 `_write_text_atomic()` 使用文本模式写盘，自动把 `LF` 转为 `CRLF`；如果模型内容本身含 `CRLF`，还可能形成二次转换。因此数据库内容与登记哈希一致，实际 Artifact 文件字节却不一致。当前 Run 7 份 Artifact 全部命中，扩展扫描确认历史 89 份已物化 Artifact 均受影响。

已修改 `server/app/platform_store.py`：原子写入统一先编码为 UTF-8 bytes，再用字节接口写入，后续不再发生平台隐式换行转换。启动修复只处理“数据库内容原始字节哈希与登记哈希一致、但物化文件不一致”的可证明存储偏差，不修改 Artifact 内容、版本或登记哈希；每次修复写入 `artifact.storage.repaired` 事件，记录旧观测哈希、登记哈希、路径、字节数和原因。

第 6 版当前 Run 的 7 个修复事件为 sequence 4802–4808。全库复算结果为 `artifacts=89, mismatch_after_repair=0`，两位审计人物重新获得的 `artifact-registry.json` 均为 `count=7, mismatch=0`。新增测试覆盖混合 `LF/CRLF` 原始内容的精确字节落盘，以及旧版换行转换文件在重启时的单次可审计修复；定向结果 `2 passed`。
