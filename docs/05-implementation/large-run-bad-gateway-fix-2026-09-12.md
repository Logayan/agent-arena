# 大型 Run 详情导致 Bad Gateway 的修复记录

日期：2026-09-12

## 现象

- 前端 `http://127.0.0.1:5173` 正常，但 `/api/*` 间歇返回 `502 Bad Gateway`。
- 后端 `8003` 有时未监听，有时虽然监听但健康检查超时。
- 大型 Run `run_9226059d74a1` 的详情读取会长时间占用后端进程。

## 根因证据

- 该 Run 当时累计约 2.1 万条事件，事件载荷约 90 MB。
- `GET /api/platform/runs/{run_id}` 原来一次性读取全部事件，并递归生成浏览器安全投影。
- 节点卷宗会再次引用事件；多个详情请求并发时，内存和 CPU 被成倍放大。
- Windows 本地重启期间还发现遗留 Uvicorn 子进程占用 `8003`，新实例无法成为唯一服务进程，Vite 因而返回 502。

## 修复决策

1. 浏览器详情默认只读取最新 500 条事件，并返回：
   - `event_count_total`：数据库中的完整事件总数；
   - `events_truncated`：当前响应是否为窗口视图。
2. 完整事件仍保存在 SQLite，不修改内部执行器的全量读取语义。
3. 详情接口支持显式请求 100 至 5000 条事件，避免无上限浏览器响应。
4. 将详情处理改为 FastAPI 同步端点，由线程池执行，防止阻塞主事件循环。
5. 使用进程内锁限制大型详情投影并发度，避免并发请求造成内存倍增。
6. 前端轮询间隔依据 `event_count_total` 决定，不因窗口视图误判为小型 Run。
7. 清理本项目遗留的 `uvicorn ... --port 8003` 及其 Claude bridge 子进程，只保留一个后端实例；持久化 Run 由启动恢复机制接续。

## 验证结果

- 后端专项测试：`2 passed`。
- 新增测试验证两个慢详情请求被串行处理，且健康检查不被阻塞。
- Python 编译检查通过。
- `git diff --check` 通过。
- 前端 `vue-tsc -b && vite build` 通过。
- Windows 本地现场：
  - `/api/health`：`200`；
  - 前端代理 `/api/platform/git-delivery-configs`：`200`；
  - 前端代理大型 Run 详情：`200`，约 2.99 秒；
  - 返回事件 500 条、总事件 21411 条、`events_truncated=true`；
  - 详情返回后的健康检查：`200`，约 13 毫秒；
  - 后端工作进程内存约 158 MB。

## 运行现场说明

- `run_9226059d74a1` 当前为 `failed / execution_failed`，其原事件和产物仍保留。
- `run_bda13e93b2ea` 当前由唯一后端实例继续从持久化现场执行。
- 本次修复没有创建宿主仓库 Commit、Push 或 MR；Git 交付应由明确的仓库交付动作产生，不能伪造远端凭据。
